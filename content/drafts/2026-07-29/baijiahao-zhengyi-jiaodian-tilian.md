# 争议焦点怎么提炼才检索得准？四步把案情拆成检索条件，律师可套用清单

争议焦点提得准不准，直接决定后面那一轮类案检索是白干还是有用。检索搜不到能用的案例，很多人第一反应是数据库不好使、检索式不会搭，但真正卡住的地方往往更靠前：焦点还没提对，手已经开始敲关键词了。这篇不讲检索技巧，只讲检索之前那一步——怎么把一堆案情材料拆成一个能拿去检索的争议焦点，焦点提偏之后会以什么形态暴露出来，以及确认好的焦点怎么原样落成检索条件。文末给一份可以直接照着走的自查清单。

先给结论：争议焦点不是"当事人在吵什么"，而是"法官必须先回答哪一个问题，判决结果才能定下来"。这两句话听着接近，落到检索上差别极大。提在诉求层面，检索会给你一堆案由相同、裁判逻辑却完全不同的判决；提到法律适用分歧层面，检索才可能给你真正可比的类案。

## 一、焦点提偏了，检索越精准越危险

先说清楚为什么这一步值得单独花时间。

类案检索的失败有两种形态。第一种是**搜不到**——检索式太窄、关键词用了己方话术、案由选错，屏幕上一片空白。这种失败其实是良性的，因为它会报错，你立刻知道要回头改。

第二种是**搜到一堆看着很像、实际不可比的判决**。这种失败不报错。焦点提在"合同该不该解除"这种粗颗粒上，检索系统会非常高效地把几百份同案由判决推到你面前，每一份读起来都相关。你从里面挑三五份写进检索报告，逻辑自洽、格式漂亮，直到对方或者法官指出：这几份的争议点是履行不能，你的案子争的是根本违约的认定标准，两码事。

**检索引擎不会替你判断可比性，它只负责按你给的条件把最像的捞上来。** 条件本身偏了，它偏得比你还努力。所以这一步的性价比很高：多花二十分钟把焦点提清楚，能省掉后面几个小时读不可比案例的时间，还能挡掉一次庭上的被动。

## 二、先把三个层次分开：案由 ≠ 法律关系 ≠ 争议焦点

实务里这三个词经常混着用，一混，检索条件就搭不准。分开看：

**案由**是立案时给案件贴的分类标签，解决的是"这个案子归哪一类"。它是检索的**入口**，不是焦点。买卖合同纠纷底下什么争法都有。

**法律关系**是当事人之间实际成立的那层关系，解决的是"按哪套规则来"。同一个案由底下法律关系可能不同：一份"服务合同纠纷"，实质可能是承揽、可能是委托，规则不一样，检索方向就不一样。法律关系定错，后面全错。

**争议焦点**是在法律关系确定之后，双方对某个**具体要件或某条规则怎么适用**产生的分歧，解决的是"这个案子到底卡在哪儿"。它才是可比性的真正尺度。

一个简单的检验办法：**把你提的焦点拿去问"回答了它，判决方向是不是就定了一大半"。** 如果不是，说明你提的还停在案由或诉求层面，得继续往下拆。

## 三、四步提炼法

### 第一步：把案情切成"不争的"和"争的"

拿一张纸分两栏。左栏写双方都认的事实——签了什么、付了多少、哪天交的货。右栏写有分歧的部分。这一步的价值在于**把工作量砍掉大半**：不争的事实不产生焦点，也不需要检索。

分歧本身还要再分一层：

- **事实分歧**：这笔钱到底付没付、这份签字是不是本人。往下走的是举证责任和证据规则。
- **法律分歧**：事实都认，但这些事实在法律上算不算构成违约、算不算表见代理。往下走的是法律适用。

**两类分歧必须分开检索，混在一起是最常见的翻车点。** 事实分歧的类案，要看同类证据结构下法院怎么分配举证责任；法律分歧的类案，要看同样的事实构造下法院怎么套要件。把这两类混成一个焦点去搜，捞回来的东西必然半数不可比。

### 第二步：把"争的"翻译成要件语言

这一步是核心。当事人和你说的是生活语言——"他答应了又反悔""东西根本不能用"。检索系统里的判决书用的是要件语言。中间不做翻译，关键词永远对不上。

做法是：先确定这个请求权的构成要件有哪几项，然后逐项问一句"这一项双方有没有分歧"。

以违约损害赔偿为例，要件大致是：合同有效成立、对方存在违约行为、己方有损失、违约与损失之间有因果关系、损失可预见。逐项过一遍，往往会发现前三项双方都没争，真正卡住的是**因果关系**或者**可预见性范围**。那么焦点就落在这一项上，检索条件也应该围绕这一项组织，而不是围绕"违约赔偿"这个大词。

抗辩事由同理：对方主张的是诉讼时效已过、还是不安抗辩、还是情势变更？这些各自是独立的焦点，各自有各自的类案群。

**判断这一步做到位没有：你提出来的焦点，应该能直接用判决书"本院认为"部分会出现的措辞写出来。** 如果写出来的句子只在你的代理词里会出现，说明还没翻译完。

### 第三步：把焦点收窄到具体分歧点

翻译成要件语言之后，通常还是太宽。"是否构成表见代理"是一个要件级的问题，但真正决定胜负的往往是它底下更细的分歧：相对人的善意怎么认定、有没有尽到合理审查义务、审查到什么程度算合理。

收窄的手法是给焦点加限定：

- **加事实特征**：不是"是否构成表见代理"，而是"业务员持有公章但无授权书，相对人未核实的，是否构成表见代理"。
- **加法律关系类型**：同一个规则在不同合同类型下裁判尺度可能不同。
- **加时间切片**：法条或司法解释修订过的，要说明按哪个版本讨论。

收窄到什么程度算够？**一个可操作的标准是：这句话拿去检索，捞回来的判决你随手翻三份，三份争的都是同一件事。** 做不到就再收一层。

### 第四步：把焦点原样落成检索条件

焦点定了，转成检索条件的时候有一条纪律：**尽量原样搬，不要重新组织语言。** 每多一次转述，就多一次偏移的机会。

一个可以照抄的映射关系：

| 焦点里的成分 | 落到检索里的位置 |
|---|---|
| 法律关系类型 | 案由筛选 |
| 要件名称、规则表述 | 全文关键词（用判决书措辞，不用己方话术） |
| 事实特征 | 附加关键词，用来收窄 |
| 法条版本 | 裁判日期区间（切到修订生效之后） |
| 想要的说服力层级 | 法院层级、审理程序筛选 |
| 事实分歧还是法律分歧 | 决定关键词落在证据规则还是要件认定上 |

多说一句关于关键词的：**用法院的话，不用当事人的话，也不用自己的话。** "他一直拖着不给"在判决书里叫"迟延履行"，"东西是坏的"叫"标的物质量不符合约定"。这个转换做不好，检索式再复杂也搭不出结果。

## 四、五种典型的提偏形态，对照自查

**1. 把诉求当焦点。** "原告要求被告支付货款 XX 元"是诉讼请求，不是争议焦点。焦点是这笔货款该不该付、为什么不该付。诉求当焦点去检索，等于按案由检索，颗粒度差了两级。

**2. 停在案由层面。** "民间借贷纠纷中借贷关系是否成立"这种表述，看着像焦点，实际还是分类标签。借贷关系不成立有很多条路径——大额现金交付未举证、名为借贷实为投资、虚假诉讼，每条路径的类案群完全不同。

**3. 一次提七八个焦点，不排序。** 案子复杂的时候确实会有多个焦点，但它们的权重不一样，而且**有先后依赖**：法律关系性质不定，后面的要件问题根本不用讨论。正确做法是排出主次和先后，主焦点重点检索，次焦点简单核一轮。全都平均用力，时间会耗在无关紧要的分支上。

**4. 事实分歧和法律分歧混成一个焦点。** 前面说过，这两类的类案不可互换。表现是检索结果里一半判决在讨论证据，一半在讨论要件，你读了半天觉得"好像都相关又都不太对"。

**5. 用己方话术表述焦点。** 代理词里的措辞是有立场的，判决书是中性的。焦点表述带了立场，一是检索关键词对不上，二是更麻烦——**你会只搜到支持自己的那一半，对不利判决完全无感**，直到对方甩出来。做焦点检索的时候，有意识地把表述反过来再搜一轮，是很值的一步。

## 五、焦点不是一次定死的，检索结果要反过来校正它

实务里一个很有用的习惯：**把焦点提炼和检索当成一个循环，而不是两个先后步骤。**

第一轮检索捞回来的判决，除了看能不能用，还要看一件事——**法院自己是怎么归纳这个焦点的**。判决书"本院认为"开头那句"本案的争议焦点为……"，是法官对同类案件的标准表述。如果你发现同类判决普遍把焦点归纳成 A，而你提的是 B，那大概率是你偏了，而不是法院都偏了。

这一步的收益很直接：**照着法院的归纳方式改写焦点，再搜一轮，命中率会明显不一样。** 因为你终于在用系统里那批文书的语言说话了。

另一种情况是：搜了几轮，同类案件的焦点归纳分成明显的两派。这本身就是重要发现——说明这个问题存在裁判分歧，检索报告里应该把两派都呈现出来，并说明本辖区倾向哪一派。把分歧藏起来只报有利的那派，是检索报告最容易被识破的短板。

## 六、工具帮得上什么，帮不上什么

先说帮不上的：**焦点提炼这件事本身，交不出去。** 它需要对案情负责、对策略负责，AI 可以给你一份候选清单，但选哪个作主焦点、怎么排序，是执业判断。

能帮上的主要是三段：

- **从卷宗里把要素抽出来**，当事人、时间、金额、关键行为，省掉手工摘录。但抽出来的要素要回原页核过再用——要素错了，焦点跟着错。
- **把焦点落成检索条件之后逐层收窄**，按案由、法院层级、审理程序、裁判日期一层层筛，实时能看到还剩多少篇。这一步纯体力，交出去很划算。
- **把同类判决的焦点归纳批量看一遍**，用来做第五节说的反向校正。

选型的时候，围绕这条链路有几个问题值得问清楚：

1. 检索结果能不能直接看到判决书里的焦点归纳段落，而不是只给标题和摘要？
2. 筛选条件叠加的时候，能不能实时显示剩余篇数？看不到剩余量，就没法判断收窄到哪一步该停。
3. 每条结果能不能一键回到裁判文书原文？回不去原文，后面的核验全做不了。
4. 从阅卷抽出来的要素，能不能直接带进检索条件，中间不用人工重新敲一遍？多一次转述就多一次偏移。
5. 库里的数据规模和覆盖范围是什么口径？亿级规模下小众争议点也能出结果，样本太薄的库在这类问题上会给你一个"本地没有同类案件"的假结论。

这几个问题不针对具体某家产品，是这条工作流本身提出来的要求。拿本单位真实办过的案子去试，比看演示样例可靠得多——**你知道答案，才看得出它漏了什么。**

## 七、可套用清单

提炼阶段：

- [ ] 案情已切成"不争的"和"争的"两栏
- [ ] "争的"部分已分成事实分歧和法律分歧，分开处理
- [ ] 已按请求权构成要件逐项过筛，定位到真正有分歧的那一项
- [ ] 焦点用要件语言表述，句子像判决书"本院认为"里会出现的措辞
- [ ] 焦点已加事实特征、法律关系类型、法条版本三类限定收窄
- [ ] 多焦点已排出主次与先后依赖，不平均用力
- [ ] 焦点表述中性，没有夹带己方立场

落成检索条件：

- [ ] 法律关系 → 案由筛选
- [ ] 要件与规则表述 → 关键词（用法院措辞）
- [ ] 事实特征 → 收窄用的附加关键词
- [ ] 法条版本 → 裁判日期区间
- [ ] 说服力需求 → 法院层级与审理程序筛选
- [ ] 焦点原样搬进条件，没有中途重新组织语言

反向校正：

- [ ] 看过同类判决里法院自己怎么归纳焦点
- [ ] 己方表述与法院普遍归纳有出入的，已按法院的说法改写重搜
- [ ] 有意识地反向搜过一轮不利判决
- [ ] 发现裁判分歧的，两派都已记录，未只留有利的一派

一句话收尾：类案检索的准确度，一大半在敲第一个关键词之前就已经决定了。焦点提对，普通的检索条件也能捞到能用的判决；焦点提偏，再精巧的检索式也只是把你更快地带向一批不可比的案例。
