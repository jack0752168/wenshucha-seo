# 为什么律所买了利冲系统，还是会出利益冲突的事故？

> 状态：✅ 已成稿，⏸️ **本轮未投**——今日知乎专栏已发 2 篇（07:44:55 / 08:27:38，members/articles API 实证），已达文章区当日上限约 2 篇。留待次日轮次投递。
> 与当日百家号篇（1874486621362502427）同话题不同角度：百家号答「检索动作怎么做才不漏」，本篇答「为什么系统不背这个锅」——从系统能力边界反推。

结论先说：利冲事故基本不是"没查"造成的，是"查了，但系统只能替你查它知道的那部分"。系统负责匹配字符串，判断主体是不是同一个、构不构成冲突，从来都是人的活。买系统解决不了这一步。

一、系统能回答的问题，比你以为的窄

所里的利冲库回答的是一个很具体的问题：这个字符串，在本所的案件记录里出现过没有。

它默认了两件事：第一，你输进去的名字就是这个主体在所有记录里的写法；第二，本所的案件记录就是判断冲突所需要的全部信息。这两个默认都不成立，事故就是从这两个缝里漏出来的。

二、第一个缝：一个主体不止一个名字

公司会改名，改名之前的合同和官司仍挂在旧名下；内部录入的人会用简称，同一家公司在三个项目里可能存成三种写法；委托人是母公司，冲突却出在子公司；自然人重名，命中一堆和命中零条一样没法用。

这几类都不需要谁失职就会发生，它们是记录本身的性质。所以正确的做法是把"一个主体"先拆成一串检索词——每个曾用名、每个简称、每一层关联方（股东、法定代表人、实际控制人），双方都拆——再逐个跑。慢，但这是唯一能收敛的办法。

三、第二个缝：本所的库只记得本所办过的案子

这个缝更结构性。利冲库能告诉你"本所跟这个主体有没有过关系"，它没法告诉你"这个主体在外面是什么样的当事人"——过去涉过哪些诉讼、跟谁打的、对手里有没有本所现在或曾经的客户。

补这半边只能靠公开裁判文书检索：把拆好的每个名称、每层关联方，都到公开判决里过一遍，看它以什么身份出现过、对手是谁。这不是替代利冲系统，是补它拿不到的数据。

顺带一个容易踩的坑：公开文书对当事人名称的写法本身就不统一，同一主体在不同法院、不同年份的文书里可能写全称、可能写"以下简称某某"、也可能带"原名"的括注。不预设这一点，很容易把"搜不到"当成"没有"。

四、报告只写结论，等于没留痕

"经检索，未发现利益冲突"——这句话在事故复盘时什么都证明不了。没人知道当时查了哪几个名字、哪几个库、哪些查了没结果、哪些压根没查。

至少记四样：检索对象清单（含每个曾用名/简称/关联方，注明来源）、检索范围、每一项的命中或未命中（未命中要单独写）、以及明确排除在外的部分。最后一样最容易被省，也最重要。

五、这套做法的局限（必须说清楚）

第一，公开裁判文书只覆盖走到法院并且公开的那部分纠纷。协商解决、调解结案、走仲裁的多数不在里面。所以"在公开判决里没查到涉诉"只等于"没有检索到公开的生效判决"，不等于这个主体没有过纠纷。这两句话在报告里必须分开写。

第二，公开文书的年份和地区分布并不均匀，某主体近年案件没被检索到，也可能只是那部分文书没公开，撑不起"它最近没打官司"这种趋势判断。

第三，名称匹配替代不了实质判断。检索只把候选摊到桌面上，是不是同一主体、构不构成冲突，最终要由承办律师和所里的利冲审查环节定。

第四，这套动作有成本。一个主体拆十几个检索词、跑两三个库，比贴一个全称点一下慢得多。不是每个咨询都要走完整套，但正式立项之前应该走完。

第五，利益披露：我在做公开裁判文书检索相关的产品（文书查），上面第三节的做法跟我的工作相关，看的时候可以打个折。方法本身不依赖任何特定工具，用哪家的库都成立。
