# 判决书查询工具怎么用才查得全？四种查询目标对应四套做法

判决书查询工具用不好，多数时候不是工具的问题，而是查询目标没想清楚。"查一份判决"和"查一类判决"是两件事，"查某家公司涉过哪些诉"和"查一份判决后来有没有被改判"又是另外两件事。这四种目标需要的工具能力完全不同，用查第一类的方法去查第三类，查一整天也查不全。

这篇按四种查询目标分开讲：每一种该用什么检索路径、判决书查询工具在这一类里该具备什么能力、以及哪些情况是任何工具都查不到的。写给靠检索办案的人——律师、检察官、法官助理。

## 一、先分清你要查的是哪一类

坐下来打开判决书查询工具之前，先花三十秒回答一个问题：你手上有什么，你要的是什么。

**目标一，查某一份特定判决。** 你已经知道这份判决存在——对方在答辩状里引了、当事人给了你一张判决书照片、或者你只记得大概是哪年哪个法院判的。要的是这一份的完整原文。

**目标二，查一类判决（类案）。** 你手上是一个待办案件，想知道同类争议法院一般怎么判。要的不是某一份，是一批，而且要能说清这批是怎么撈出来的。

**目标三，查某个主体涉过哪些诉。** 尽调、合规审查、或者开庭前摸对方底。要的是围绕一个公司或个人展开的全部涉诉情况。

**目标四，查一份判决后来怎么样了。** 你想引用一份判决，但必须先确认它有没有被二审改掉、有没有进再审。要的是这一份的程序走向。

这四种目标对应四套完全不同的做法。下面分开说。

## 二、目标一：查某一份特定判决——先用精确字段

这一类最忌讳的动作是打开全文检索框、把记得的案情敲进去。全文检索是在正文里做匹配，慢、散，而且你记的表述十有八九和判决书里的书面表述对不上。

**手上有案号时，直接用案号字段检索。** 案号是判决书查询工具里区分力最强的字段，格式是"（年份）＋法院代字＋案件类型代字＋案件编号"，四段齐全时基本能唯一定位。这里有两个常见的坑：一是案号里的括号是中文括号，复制粘贴时容易带成英文括号导致检索不到；二是当事人给的照片里案号常被手指或折痕挡掉一两位，与其猜，不如把确定的部分加上法院和年份一起筛。

**只有当事人名称时，用当事人字段而不是全文关键词。** 个人姓名重名多，配合案由和法院层级一起收窄；公司名称要用工商登记的全称，简称在判决书正文里出现，但在结构化字段里通常存的是全称。

**只记得法院和大概时间时，用"法院＋年份区间＋案由"三条一起筛。** 这三条同时限定后，结果量通常已经能人工翻完了。比起反复换关键词，这条路稳得多。

**判断工具是否够用的标准**：能不能按案号、当事人、法院、裁判日期做字段级检索，而不是只有一个全文搜索框。只有全文框的工具，在这一类查询上效率差一个量级。

## 三、目标二：查一类判决——检索式怎么搭

这是律师用判决书查询工具时间最长的一类，也是最容易出现"查了一堆但不敢用"的一类。核心方法是：先收窄范围，再谈关键词。

**第一步，把争议拆成检索条件，而不是拆成句子。** 一个劳动争议案件，能拆出的条件是：案由（劳动争议）、争议事项（未足额支付劳动报酬 / 违法解除）、审理程序（一审 / 二审）、法院层级、年份区间、裁判结果方向。把这些先在筛选栏里选定，剩下的结果集通常已经小了一两个数量级。

**第二步，关键词一律用判决书里的书面表述。** 当事人说"干满了没给加班费"，判决书里写的是"用人单位应支付延长工作时间工资报酬"。用口语去搜，要么命中极少，要么被迫模糊匹配，两种结果都不好。可行的做法是先撈到一两份同类判决，把"本院认为"部分反复出现的表述抄下来，作为第二轮检索式的原料。

**第三步，用第一轮结果反哺第二轮。** 第一轮的价值往往不在结果本身，而在于它告诉你这类案子的司法语言长什么样、常引哪几条法条。读三到五份，提炼术语，重搭检索式，第二轮的准确度会明显不一样。

**第四步，结果量控制在能逐条读完的规模。** 一次返回上万条说明检索式没有区分力，此时翻页是最低效的动作。加限定条件的优先顺序是：案由 → 审理法院层级 → 裁判结果 → 时间区间，每加一条重新看一次结果量，压到两三百条以内再开始逐条读。

**这一类查询对工具的能力要求最高**，至少要看四件事：能不能在全文里检索并直接定位到"本院认为"那一段（而不是只给你一个标题让你自己打开慢慢找）；能不能按案由、程序、法院层级、年份组合筛选；命中结果能不能一键点到原文核验；检索条件和命中记录能不能导出，供检索报告留痕。第四条在出具类案检索报告时是硬要求——说不清怎么搜的，报告本身就站不住。

## 四、目标三：查某个主体的涉诉情况——最容易查漏的一类

这一类的难点不在检索技术，在于"一个主体"到底包括什么。漏查通常出在下面五处：

**名称变更。** 公司改过名，判决书里记的是当时的名称。只用现名去查，改名之前的案子全部漏掉。做法是先从工商信息拉出历史名称，逐个查一遍。

**全称与简称。** 结构化字段里通常是全称，正文里可能用简称。两种都试一次，成本很低。

**关联主体。** 分公司、子公司、实际控制人、法定代表人个人涉诉，很多时候才是你真正想知道的东西。母公司名下干干净净，不代表这个集团没有争议。

**多地法院。** 一个主体的案子可能分散在注册地、经营地、合同履行地等多个法院。任何按地域默认收窄的查询，都会给出偏窄的结论。

**执行信息不在判决书里。** 判决书查询工具查的是裁判文书，被执行人信息、失信名单是另一套公开系统的内容。做尽调时把两边分开查，别指望一个入口全覆盖。

**给这一类查询的一条实用建议**：把查询过程记成一张表——查过哪些名称、用了哪些字段、每次命中多少条。尽调结论要经得起复盘，"我查过了"没有说服力，"我用这七个名称在这五类字段上查过，命中如下"才有。

## 五、目标四：查一份判决后来怎么样了

这一条是最容易被跳过、后果也最严重的一步：**一审判决不等于生效判决。** 你引用一份一审判决支撑观点，对方当庭甩出二审改判的结果，这个场面在法庭上很难看。

做法是：拿到目标判决后，用当事人名称加上法院层级往上一级再查一次，看有没有对应的二审或再审文书；同时注意判决书本身的表述——"本判决为终审判决"和"如不服本判决，可在十五日内提起上诉"是两种完全不同的状态。裁定书也要一并看，撤诉裁定、发回重审裁定都会改变一份判决的实际效力。

**引用之前的最低标准**：确认程序状态、确认没有被上级法院改变、确认所引的说理部分确实出自"本院认为"而不是当事人的诉辩主张。第三条尤其容易出错——判决书前半部分大段写的是双方各自的说法，把当事人的主张当成法院的观点引出去，是很低级但很常见的错误。

## 六、任何判决书查询工具都做不到的四件事

选型时该清楚的不只是能做什么，更是不能做什么。下面四条不针对某一家，是这类工具的共同边界。

**第一，公开范围本身有限。** 裁判文书公开有法定的例外情形——涉及国家秘密、未成年人犯罪、以调解方式结案、离婚诉讼等情形依法不上网公开。这意味着任何以公开文书为底的查询结果，都不等于"全部同类案件"。

**第二，做不了统计推断。** 一个案由下撈到的一百份判决，是"公开的、被检索式命中的一百份"，不是这类案件的随机样本。用它算胜诉率、算平均判赔额，方法上就不成立。可以说"检索到的这批里多数如何"，不能说"这类案件的胜率是多少"。

**第三，AI 摘要不能替代原文。** 现在多数判决书查询工具都带了 AI 摘要和要点提取，这些功能确实省时间，但生成的内容必须回原文核对。写进法律文书的每一句引用，都要能点回原判决的对应段落。工具能不能做到这一点，是选型时该当场验的。

**第四，覆盖时间和地区不均衡。** 不同年份、不同地区的上网比例不一样，用"某地这类案子少"倒推"某地不常发生这类争议"，逻辑上不成立。

## 七、一份可套用的自查清单

每次用判决书查询工具之前，过一遍下面九条：

- [ ] 我这次的查询目标属于哪一类（特定一份 / 一类 / 某个主体 / 程序走向）
- [ ] 手上有没有精确字段（案号、当事人全称、法院、日期），有就先用字段而不是全文
- [ ] 关键词用的是判决书里的书面表述，不是当事人的口语
- [ ] 筛选顺序是先案由和程序，后关键词
- [ ] 结果量压到能逐条读完的规模，而不是靠翻页
- [ ] 查主体时覆盖了历史名称、全称简称、关联主体、多地法院
- [ ] 打算引用的判决确认过程序状态，没有被二审或再审改变
- [ ] 引的是"本院认为"部分，不是当事人的诉辩主张
- [ ] 检索条件和命中结果留了痕，能复盘、能写进检索报告

九条里有七条和工具无关，是方法。真正需要工具帮忙的只有两处：字段级检索能力、以及从结果一键回到原文的能力。选型时盯住这两条，比比数据规模有用得多。

## 八、我们自己在这件事上的位置

利益相关先披露：我们自己做裁判文书检索系统（文书查），所以上面对"可核验"的强调确实带着产品视角。

目前收录裁判文书约 1.6 亿份，覆盖刑事、民事、行政、执行、赔偿五大类，支持案号、当事人、法院、案由、年份等字段组合检索与全文检索，命中结果可以直接点到原文核对，也支持在律所或机关内网做私有化部署，提供免费试用。我们把"可核验"当成基本要求而不是卖点，原因就在第六节第三条——工具做不到回原文，后面的核验工作一点都省不掉，只是把时间从"查"挪到了"核"。

不管最后用哪一家的判决书查询工具，有两个问题建议在试用阶段当场验一次：随便挑一条命中结果，能不能三次点击之内看到原判决全文；一次检索的条件和结果，能不能原样导出留痕。这两条谁都能当场演示，演示不出来的，宣传里的其他数字也不必太当真。工具是次要的，把查询目标拆清楚才是省时间的大头。想自己试一下的，站点是 wenshucha.com。
